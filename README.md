# KV Action Expert prototype

This is the first PyTorch prototype for the idea in `idea_notes/Llm_action_expert.md`.
It freezes an instruction-tuned causal-LM backbone during **prefill**, extracts
its actual per-layer key/value cache, and trains a separate, small causal
Transformer to emit the next tool call. Context is rendered with Qwen3's native
tool template and ends exactly at `<tool_call>`; the expert predicts only the
JSON body and literal `</tool_call>` terminator, never `<think>` content. The
expert never receives prompt text or tool schema as tokens—only the backbone KV
memory. Input/output token embeddings are borrowed from the frozen backbone.

## Recommended first experiment

Download the gated `Salesforce/APIGen-MT-5k` dataset (accept its CC-BY-NC-4.0
terms) and use `Qwen/Qwen3-4B` as the default backbone. It is a current Qwen3
dense model with 36 layers and GQA (32 attention heads / 8 KV heads), making it
a much more meaningful semantic backbone for this hypothesis. APIGen-MT
provides 5,000 verified multi-turn tool trajectories in the ShareGPT-like
format consumed by this repository. If VRAM is tight, use `Qwen/Qwen3-1.7B`
for debugging only; it is a 4.08 GB download.

```bash
conda create -n kvx python=3.10 -y
conda activate kvx
python -m pip install --upgrade pip

# H200 / CUDA 12.6 tested wheel. For another CUDA platform, install the
# matching PyTorch wheel first, then keep the remaining requirements unchanged.
python -m pip install torch==2.7.1 torchvision==0.22.1 --index-url https://download.pytorch.org/whl/cu126
python -m pip install -r DUAL_LLM/requirements.txt
huggingface-cli login                         # needed for APIGen-MT terms
python DUAL_LLM/scripts/download_data.py \
  --dataset Salesforce/APIGen-MT-5k --out DUAL_LLM/data/apigen_mt_5k.json
huggingface-cli download Qwen/Qwen3-4B \
  --local-dir DUAL_LLM/models/Qwen3-4B
```

For the paper-scale setting, retain this exact implementation and switch the
backbone to a larger current Qwen3 model; use APIGen-MT for controlled
ablations, then add a normalized ToolBench trajectory dump. Do not train or evaluate on
APIGen-MT for commercial use: its stated license is non-commercial.

## NatureBench coding-agent trace finding (2026-08-14)

We profiled a deterministic 75-trajectory sample from NatureBench (15 each of
Claude Code Opus 4.6, Opus 4.7, Qwen 3.7 Max, and Codex GPT-5.4/5.5), using the
Qwen3-4B tokenizer. The denominator is **model-emitted visible content only**:
reasoning, ordinary assistant text, and serialized tool name plus input. Tool
results are explicitly excluded. The reproducible report is
[`runs/naturebench_action_profile_by_tool_sample75.json`](runs/naturebench_action_profile_by_tool_sample75.json).

| Category | Qwen-token proxy | Share of model-emitted visible tokens |
| --- | ---: | ---: |
| Bash | 1,497,450 | 28.5% |
| Write | 1,347,087 | 25.6% |
| exec_command | 458,572 | 8.7% |
| Edit + apply_patch | 463,695 | 8.8% |
| Other tool inputs | 202,599 | 3.9% |
| **All tool inputs** | **3,969,649** | **75.6%** |
| Reasoning | 1,142,646 | 21.8% |
| Ordinary assistant text | 140,776 | 2.7% |

This corrects an easy-to-make interpretation error: short shell/read calls are
numerous but are not the central token source. The large share comes primarily
from code-bearing `Write`, `Edit`, `apply_patch`, and long `Bash` commands.
For Qwen 3.7 Max alone the all-tool-input share is 68.1%; the 90%+ Codex share
is not directly comparable because Codex reasoning text is encrypted in these
logs. “Tool input” includes the `content` field of `Write`, because those code
tokens must be generated by the model; it never includes the returned command
output.

**Decision.** The speed hypothesis remains plausible for coding-agent traces,
but only if the Action Expert can reliably replace long code-bearing tool
arguments. Replacing only short, highly structured API/shell calls is unlikely
to save enough compute to justify the routing overhead. APIGen-MT is therefore
a protocol/KV-interface sanity benchmark, not evidence for this coding-agent
claim. A paper-scale experiment needs a pretrained small code Action Expert,
code-tool trajectory training data, and end-to-end metrics: executable-file or
patch-application rate, task success, and closed-loop latency—not just
teacher-forced action loss.

## Run

```bash
# Default formal run: two-GPU DDP (H200-oriented; batch size 16 per GPU).
bash DUAL_LLM/run.sh

# Fast structural check, no model or dataset download required.
python DUAL_LLM/scripts/smoke_test.py

# 90/10 deterministic split; first run is intentionally modest.
python DUAL_LLM/scripts/train.py \
  --data DUAL_LLM/data/apigen_mt_5k.json \
  --backbone Qwen/Qwen3-4B \
  --output DUAL_LLM/runs/qwen3_4b_kv \
  --max-context-tokens all --max-action-tokens 192 \
  --expert-width 1024 --expert-layers 36 --expert-heads 8 \
  --kv-layers all --kv-tokens all --epochs 3 --batch-size 16 \
  --wandb-project dual-llm-kv-action --wandb-run-name qwen3-4b-kv-ar

python DUAL_LLM/scripts/evaluate.py \
  --data DUAL_LLM/data/apigen_mt_5k.json \
  --checkpoint DUAL_LLM/runs/qwen3_4b_kv/best.pt \
  --backbone Qwen/Qwen3-4B

# Closed-loop, multi-turn trajectory latency. Generated calls become the next
# prompt's history; APIGen observations are replayed (no external API time).
CUDA_VISIBLE_DEVICES=1 python DUAL_LLM/scripts/rollout_trajectory.py \
  --data /data/datasets/datasets-hf/APIGen-MT-5k/apigen-mt_5k.json \
  --backbone /data/datasets/models-hf/Qwen3-4B \
  --checkpoint DUAL_LLM/runs/qwen3-4b-native-kv-resumed/best.pt \
  --trajectory-index 2 --print-predictions
```

`run.sh` launches PyTorch DDP with two GPUs by default. `BATCH_SIZE` is per GPU,
so the default effective global batch is 32. It accepts environment-variable
overrides without editing it, for example
`CUDA_VISIBLE_DEVICES=0,1 BATCH_SIZE=8 RUN_NAME=qwen3-4b-kv-bs8 bash DUAL_LLM/run.sh`.
Use `NUM_GPUS=1` for a single-card debug run.

The default optimizer uses 200 linear warmup updates followed by cosine decay
to 10% of the initial learning rate. To initialize a new run from a previous
Action Expert checkpoint while restarting optimizer and scheduler state, use
`RESUME_FROM=runs/old/best.pt RUN_NAME=continued bash run.sh` from `DUAL_LLM/`.
At every epoch, rank 0 writes `epoch_001.pt`, `epoch_002.pt`, and so on; it also
maintains `last.pt` and validation-selected `best.pt`.

The default is a Pi05-inspired, layer-synchronous pair: Pi05 creates a narrow
Gemma-300M expert with the standard Gemma implementation and injects the
prefix tower's KV cache into it. We preserve that principle for Qwen3-4B: the
Action Expert is an official Transformers `Qwen3Model` initialized from
scratch, with Qwen-aligned 36 layers but width 1024 rather than Qwen's 2560.
It uses Qwen3 RMSNorm, QK-normalization, SwiGLU, RoPE and incremental cache
decode, rather than a hand-written Transformer block. It has eight 128-d KV
heads, exactly matching Qwen3-4B's eight KV heads and 128-d head size, so each
expert layer directly consumes its corresponding layer's unprojected KV cache.
`--max-context-tokens all --kv-tokens all` retains every native Qwen prompt
token and every corresponding KV cache entry; this is the default.
Length-aware batching groups similarly sized trajectories to avoid padding
short inputs up to a long one. The frozen prefill calls Qwen's decoder directly
and never materializes vocabulary logits for prefix tokens; only the KV cache is
kept. The training log reports loss; `evaluate.py` reports tool-name accuracy,
canonical JSON exact match, and valid-JSON rate with greedy decoding on the
same held-out split. The important interface ablation is a second training run
with `--representation last_hidden`; it gives the same expert only final hidden
states rather than attention KV.

Training writes step loss/learning rate and epoch train/validation loss to
Weights & Biases. Run `wandb login` once before an online run. Add
`--wandb-mode offline` on a machine without W&B network access, or
`--wandb-mode disabled` to turn tracking off. Step metrics are logged every 50
optimizer steps by default; tune this with `--wandb-log-interval`.

Changing `--expert-arch` changes the entire trainable tower. The current
default is `qwen3`; legacy checkpoints trained with the earlier custom expert
carry `"expert_arch": "custom"` implicitly and remain evaluable, but cannot
initialize a Qwen3-expert run. Train the Qwen3 expert from scratch.

## Data contract

The loader accepts the official APIGen-MT records directly. It first performs a
deterministic 90/10 split over the 5,000 original trajectories, then expands
each split separately into decisions—so no trajectory crosses train/validation.
By default APIGen's synthetic `think` function is excluded from both tool schema
and supervision; it is not an external tool action. Every remaining decision's
native-Qwen prompt contains system policy, tools, all preceding external calls
and observations, and ends at `<tool_call>`. Its target JSON body is, e.g.

```json
{"name":"get_reservation_details","arguments":{"reservation_id":"C6X779"}}
```

The decoder training sequence appends `</tool_call>` after that JSON; evaluation
stops at this literal tag rather than relying on EOS.

`rollout_trajectory.py` is the user-driven latency protocol for the multi-turn
setting. Qwen writes every assistant turn; in `--mode hybrid` it is intercepted
only when Qwen itself emits `<tool_call>`, and the AE receives that live Qwen
KV cache to write the call body. `--mode qwen` is the direct full-Qwen baseline.
The rollout now keeps one Qwen KV cache across the complete trajectory. New
user/tool-template suffixes are block-appended; after hybrid AE generation, the
AE action tokens are passed through Qwen once to synchronize the Qwen history
KV. It reports model load time separately from `rollout_wall_s`, and splits the
latter into initial prefill, history append, Qwen decode, AE decode, action-KV
synchronization, and host-side overhead. The detailed JSON report is written
beside the checkpoint. APIGen has logged observations,
not executable local tools, so strict mode (the default) replays one only when
the generated call exactly matches the next logged call; a mismatch receives a
local error instead. `--tool-result-mode oracle-next` is available only as a
controlled latency upper bound. Multiple trajectories can be benchmarked with
repeated `--trajectory-index` options.

The first persistent-cache check on trajectory 0 (one H200, bf16, excluding
model load and tool execution) produced:

| Mode | Rollout wall | Tool calls | Exact match |
| --- | ---: | ---: | ---: |
| Qwen3-4B | 12.33 s | 3 | 33.3% |
| Qwen3-4B + trained AE | 9.27 s | 1 | 100% |

These numbers are a protocol check, not a quality claim: the full Qwen model
hallucinates extra calls on this trajectory, so its wall time includes more
generated tokens. Reports: `runs/e2e_qwen_trajectory_0_persistent_test.json`
and `runs/e2e_hybrid_trajectory_0_persistent_test.json`.

A second persistent-cache check on APIGen trajectory 6 (a transfer-to-human
case) also completed without cache/template errors:

| Mode | Rollout wall | Tool calls | Tool-name accuracy | Exact match |
| --- | ---: | ---: | ---: | ---: |
| Qwen3-4B | 5.69 s | 2 | 100% | 50% |
| Qwen3-4B + trained AE | 3.70 s | 2 | 100% | 0% |

The hybrid AE generated a semantically plausible but target-nonidentical
summary argument on this instance; `canonical_exact_match` is a strict JSON
match, not a semantic judge. Reports: `runs/e2e_qwen_trajectory_6_persistent_test.json`
and `runs/e2e_hybrid_trajectory_6_persistent_test.json`.

## Measured action-decode throughput (2026-08-14)

The measurements below use one H200 NVL, bf16, Qwen3-4B, APIGen native-Qwen
tool prefixes (mean 3.8k prefix tokens), and a forced 128-token action suffix.
They measure **only suffix decode throughput**: model loading, Qwen prefix
prefill, request queueing, tool execution, and tool-result insertion are
excluded. To isolate GPU batch compute from padding, each real prefix is
repeated within its batch. Thus these are upper-bound serving-throughput
figures, not the latency of one independent agent request.
`benchmark_action_decode.py` does **not** implement dynamic agent batching:
every row is a homogeneous repeated prefix after it has already reached the
tool-call boundary. `rollout_trajectory.py` is intentionally single-trajectory
and sequential. A real batched server must maintain separate Qwen-active and
AE-active queues, compact requests that independently reach `<tool_call>`, pad
their per-layer KV caches/masks by length bucket, and requeue each request after
its tool result. Therefore the batch-8/16 results below are not yet an
end-to-end multi-agent serving result.

| AE configuration | Decode batch | Qwen3-4B tok/s | AE tok/s | AE/Qwen |
| --- | ---: | ---: | ---: | ---: |
| Official Qwen3-like AE, random, 36×1024 | 1 | 45.44 | 48.89 | 1.08× |
| Official Qwen3-like AE, random, 36×1024 | 8 | 175.29 | 395.31 | 2.26× |
| Official Qwen3-like AE, random, 36×1024 | 16 | 195.19 | 584.52 | 2.99× |
| **Trained legacy custom AE checkpoint, 36×1024** | **1** | **45.55** | **57.07** | **1.25×** |
| **Trained legacy custom AE checkpoint, 36×1024** | **8** | **175.49** | **384.41** | **2.19×** |

The trained custom checkpoint is
`runs/qwen3-4b-native-kv-resumed/best.pt`; its weights do not materially change
decode cost. Its small batch-1 gain confirms that preserving all 36
layer-synchronous autoregressive layers largely preserves single-request
latency. The throughput gain appears only when tool-call decoding can be
batched. Reports: [random, batch 1](runs/random_qwen3_ae_speed_128t.json),
[random, batch 8](runs/random_qwen3_ae_speed_bs8_128t.json),
[random, batch 16](runs/random_qwen3_ae_speed_bs16_128t.json),
[trained custom, batch 1](runs/custom_ae_checkpoint_speed_bs1_128t.json), and
[trained custom, batch 8](runs/custom_ae_checkpoint_speed_bs8_128t.json).

Reproduce a checkpoint-matched measurement with:

```bash
CUDA_VISIBLE_DEVICES=1 python scripts/benchmark_action_decode.py \
  --data /data/datasets/datasets-hf/APIGen-MT-5k/apigen-mt_5k.json \
  --backbone /data/datasets/models-hf/Qwen3-4B \
  --checkpoint runs/qwen3-4b-native-kv-resumed/best.pt \
  --decode-tokens 128 --batch-size 8 --warmup-examples 1 --num-examples 2
```

`benchmark_action_decode.py` defaults to the retained Qwen3-like expert with
random weights. When `--checkpoint` is supplied, it reconstructs the exact
saved AE architecture; old checkpoints without `expert_arch` are interpreted
as `custom`. For new training, select the architecture without code changes:
`EXPERT_ARCH=qwen3 bash run.sh` (default) or `EXPERT_ARCH=custom bash run.sh`.

Reproduce with:

```bash
CUDA_VISIBLE_DEVICES=1 python scripts/evaluate.py \
```

### Fully self-generated strict rollout: trajectory 0

For an end-to-end check, trajectory `0` was rerun with `--max-new-tokens 512`.
Only logged human messages are supplied; all assistant text and calls are
generated online. Both runs use strict replay, so no external API/tool time is
included. The full-Qwen path takes 12.63 s (three generated calls, one exact);
the hybrid path takes 12.30 s (one generated call, exact). The hybrid call is
`get_reservation_details(reservation_id="0U4NPP")` and receives its logged
observation before Qwen generates the remaining assistant text. Reports:
[full Qwen](runs/e2e_qwen_trajectory_0_512.json) and
[hybrid](runs/e2e_hybrid_trajectory_0_512.json).

These wall times are **not a fair speedup claim**, because the models produced
different trajectories: full Qwen generated two additional incorrect calls,
while hybrid did not. They only verify the intended protocol: no assistant turn
is teacher-forced, AE is activated by Qwen's emitted `<tool_call>`, and Qwen
continues from the resulting tool history. A valid end-to-end latency comparison
needs matched generated action lengths, or a verified/speculative protocol that
forces both paths onto the same accepted continuation.

### Qwen3.5-9B agent baseline: trajectory 0

Qwen3.5-9B is a stronger native agent baseline than the frozen Qwen3-4B used
above. Under the same strict self-generated protocol it produced one native
XML-style call,
`get_reservation_details(reservation_id="0U4NPP")`, which exactly matches the
logged call. It completed the trajectory in 13.62 s after model load (340
generated tokens; tool execution excluded). The detailed generated conversation
is in [e2e_qwen35_9b_trajectory_0.json](runs/e2e_qwen35_9b_trajectory_0.json).

```bash
CUDA_VISIBLE_DEVICES=1 python scripts/rollout_qwen35.py \
  --data /data/datasets/datasets-hf/APIGen-MT-5k/apigen-mt_5k.json \
  --backbone /data/datasets/models-hf/Qwen3.5-9B \
  --trajectory-index 0 --max-new-tokens 512 \
  --output runs/e2e_qwen35_9b_trajectory_0.json --print-predictions
```

Qwen3.5 is currently a **baseline only**. It is a conditional-generation VLM
with a 32-layer text tower that interleaves linear and full-attention layers;
it does not expose the Qwen3-4B-compatible per-layer attention-KV interface
assumed by the current AE. It therefore cannot be passed to `train.py` or the
Qwen3+AE rollout without a separate Qwen3.5 cache/architecture adapter.

For another source, supply JSON/JSONL records with `prompt` and either
`action` (a JSON object/string) or `target` (string). This intentionally makes
ToolBench preprocessing an explicit, auditable conversion step rather than
silently assuming one of its many released formats.
